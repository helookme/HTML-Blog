## 缘起

做这台机器的理由很朴素：想躺在床上看小说，又不想看手机。

市面上 2.9 寸的墨水屏阅读器不是没有，但要么贵，要么封闭，要么屏幕太小只能看几行。既然手上有一块嘉立创的 ESP32-C3 墨水屏开发板，就自己写一个。

最后做出来的东西是这样的：

- 2.9 寸、128×296、黑白墨水屏，一页 19 行正文
- 拨轮三键操作，长按进菜单、六秒进休眠
- 支持 30–100 万字的大书，按章加载，章节索引带缓存
- 支持 UTF-8 / GBK / UTF-16 自动识别
- 能从 BLE 翻页器学习按键并存在卡里
- 全部代码在一个 `.ino` 加两个头文件里，约 3600 行

这篇文章不写"教程"，只写这一路上真正卡住我的地方。因为教程里能查到的东西，大多不是难点；真正耗时间的，是那些没人写、也没法从例程里看出来的坑。

---

## 一、硬件：先接受它的先天条件

板子的资料很全，但读完之后必须接受几个事实：

**屏和 TF 卡共用一路 SPI。** IO1、IO4、IO6 三根线，屏那边是 DC / CLK / DIN，卡那边是 SCLK / MISO / MOSI。也就是说：**屏幕和存储卡物理上不能同时通信**。这不是软件设计选择，是布线决定的。

**IO4 的方向是反的。** 对屏它是输出（时钟），对卡它是输入（MISO）。切换时必须把 GPIO 方向重新配一遍，配不好就是"屏幕假死"或者"卡读不到"。

**卡没有独立电源。** 屏和卡共用 3.3V，没有负载开关。这意味着卡一旦被写进死状态，软件复位（CMD0）救不回来，只能整机断电。

**卡座有 CARD_DETECT 引脚，但没接到任何 GPIO。** 所以固件永远不知道"卡还在不在"，只能靠发命令试探。

这四条，基本决定了后面所有软件设计的形状。

## 二、把屏点亮

第一块屏是 2.13 寸、250×122、SSD1680。驱动用 GxEPD2，引脚按商家给的接，一次点亮。踩的坑都在细节里：

- **GPIO2 是 strapping 脚**，当 RST 用会在开机瞬间把板子带进奇怪状态，后来换到 IO0；
- **GxEPD2 的初始化和模块型号必须严格对应**，SSD1680 和 IL3820 的命令集不通用，猜错就是全白；
- **局刷和全刷的差别**不是"快慢"，而是"会不会留残影"。这块拆机屏在一直带电时局刷很干净，一旦断电再 init，第一次必须全刷。

后来换成嘉立创这块 2.9 寸（128×296，IL3820），屏幕更大、一行能放 19 行正文，体验才真正成立。

屏这一块的经验只有一句话：**墨水屏的"刷新"是有物理代价的**。全刷会闪、会响、会消耗寿命；局刷会累积残影。所以"什么时候全刷"是个必须显式设计的问题，不能交给库的默认行为。

---

## 三、软件骨架：一个按键也要有状态机

最早只有一个按键（BOOT），短按翻页、长按进菜单。后来换成拨轮，左中右三个方向，逻辑立刻复杂起来：

| 界面 | 左键 | 中键 | 右键 |
|---|---|---|---|
| 阅读 | 上一页 / 上一章 | 菜单 | 下一页 / 下一章 |
| 列表 | 光标上 | 确认 | 光标下 |
| 菜单 | 光标上 | 选中 | 光标下 |

界面一共九个状态：首页、阅读、目录、书单、图片列表、看图、菜单、跳章键盘、星标列表。每个状态都要能正确响应三个键，还要处理"长按六秒进休眠"。

这一块没有捷径，只有一条规矩：**状态迁移写成显式的 switch，而不是散落在各处的 if**。否则加一个界面就会漏掉某条返回路径，用户就会卡在某个页面里出不来。

## 四、大书：内存装不下，只能按章来

最初版本一次把整本书读进内存，上限 200KB。而实际要看的网文，动辄 3MB、300 万字、2000 多章。

这一步是整个项目第一次真正的架构改造：

**索引**：第一次打开时扫一遍全书，记下每一章的标题和字节偏移，存成缓存文件。之后打开直接读缓存，秒开。

**按章加载**：读某一章时 `seek` 到偏移，只读那一章进内存。一章几 KB，多大都能读。

**分段扫描**：一章一章扫完整本太慢，所以先扫前 30 章让用户马上能读，剩下的在后台继续扫，扫完写完整缓存。

这三件事听起来简单，但每一步都有坑：

- 扫描时**必须喂看门狗**，否则扫一本 10MB 的书会被复位；
- 扫描缓冲区不能放栈上，**8KB 的栈装不下 8KB 的缓冲区**，必须改 `static`；
- 章节标题必须**按像素宽度截断**，按字节截断会把汉字切一半；
- 章节识别不能"猜"：有些书标题写错（"第652  标题"漏了"章"字），强行识别会把正文当章节。

## 五、编码与字形：中文阅读器的隐形地雷

中文 txt 的编码是个泥潭：UTF-8、UTF-8 BOM、UTF-16LE、UTF-16BE、GBK、GB2312、GB18030。

处理方式是探测加兜底：先看 BOM，再验 UTF-8 合法性，再看 0x00 的分布判断 UTF-16，最后落到 GBK。

字形问题更隐蔽：

- 文泉驿 12px 字库里**没有中文引号、破折号、省略号、箭头**，读起来就是一个个方块。解决办法是做一张映射表，把 `“ ”` 换成 `"`、`…` 换成 `...`；
- **行尾偶尔少一个字**：原来 ASCII 一律按 6px 算宽度，但 `W`、`M` 实际更宽，算少了就会溢出被裁。后来在启动时用 `getUTF8Width()` 把 96 个 ASCII 字符的真实宽度量一遍；
- **GBK 扩展字**（非 GB2312）在 8178 字的表里没有，只能显示 `□`。

## 六、TF 卡：从丢掉 SD 库开始

这是整个项目最漫长的一段。

问题从"卡初始化失败"开始。换卡、降频、改接线都没用，最后用一段**不依赖任何库**的诊断固件，手工发 CMD0/CMD8/ACMD41/CMD58/CMD17，才看清真相：

```
CMD0  : 0x01 (idle, OK)
CMD8  : 0x01  echo=00 00 01 AA
ACMD41: 0x00 after 57 tries (ready)
CMD58 : 0x00  OCR=C0 FF 80 00     ← CCS=1，SDHC
```

底层协议是通的，挂的是 Arduino 的 `SD` 库。于是做了一个决定：**自己写一个只够用的 FAT32 驱动**。

`tf_fat.h` 最后长这样：

- 初始化：CMD0 / CMD8 / ACMD41 / CMD58，记下是不是 SDHC；
- 挂载：读 LBA0 → 找 MBR 分区 → 读 BPB → 校验 512 字节扇区、FAT32、根目录簇；
- 读：CMD17，单块 512 字节，带扇区缓存；
- 写：CMD24 + 数据令牌 + **真实 CRC16**（有些卡会校验数据块 CRC，发 `0xFFFF` 必被拒）；
- 目录：解析 32 字节目录项，支持 LFN（UTF-16 → UTF-8）；
- 写文件：只支持根目录 + 8.3 名——因为固件自己写的只有缓存、进度、星标这几个文件。

写完之后的收益是：**协议完全可控**。出了什么问题，加一行串口就能看见卡回了什么，不用猜库的内部行为。

## 七、共享总线：这台机器最难的地方

前面说过屏和卡共用三根线。真正写起来才知道有多难。

**第一个坑：`SPI.begin()` 会静默早退。** 切换设备时的写法是 `SPI.end()` 然后按新设备 `SPI.begin(...)`。但某些核心版本里，`SPI.end()` 之后 `SPIClass` 仍然认为"已初始化"，于是 `begin()` 直接 return，引脚还停在上一套配置。表现就是：切到卡之后发命令，永远回 `0xFF`，因为卡根本没有时钟。

**第二个坑：两个 CS 必须互相钉高。** 屏刷新时，如果卡的 CS 还是低电平，卡会把屏的高频时钟当成命令字节吃进去，被写乱；反过来读卡时，如果屏的 CS 是低的，屏会把卡的命令当数据。所以两边切换时都要把对方的 CS 拉高——而且是**在 `SPI.begin()` 之前钉一次、之后还要再钉一次**，因为 `SPI.begin()` 会重配引脚。

**第三个坑：CS 不能交给硬件 SS。** 把 IO21 作为 SS 参数传给 `SPI.begin()`，它会被挂到 FSPICS0 上，之后 `digitalWrite()` 不一定说了算。正确做法是传 `-1`，全程用 GPIO 手工控制。

**第四个坑：切换前要给卡"安抚时钟"。** 卡被去选中后，必须看到至少 8 个时钟才会回到 idle 状态。少了这一步，它可能停在"等数据"的状态里，然后被屏的时钟灌死。

## 八、掉卡：一次跨了六版的排查

最折磨人的症状是：**进一本书、看几页、退出来，卡就"未识别"了；刷新没用，只能整机断电。**

每一次都以为找到了原因，每一次都不是。

- 第一次怪供电，加了断电重试 —— 没用；
- 第二次怪屏带电，改成"读卡前断屏电" —— 更糟，卡彻底不应答；
- 第三次怪 CS 没钉高，两头都钉 —— 还是掉；
- 第四次抓到 `CMD0 = 0x00` 被当成失败（0x00 其实是"卡已就绪"），改成两种应答都接受 —— 好了一点，但还是掉；
- 第五次发现日志里有 `LBA = 2147508144` 这种天文数字的扇区号，加了范围检查 —— 不再乱撞卡，但还是掉；
- 第六次终于把注意力放回日志本身：**掉卡永远发生在"退出书"那一刻，而退出书只做一件事——写进度。**

真相是写卡的时序：SD 卡编程一个扇区最长需要 250ms，这期间它**根本不应答 CMD17**。而固件的逻辑是"写完 → 等 3ms → 立刻读回逐字节比对"，比对照样失败 → 判定写失败 → 重写 → 再失败 → 复位卡。**一次退出就折腾三轮，卡被写进死状态。**

这中间有一个反复出现的教训：**日志永远比猜测可靠**。`TF CMD0=00`、`LBA=2147508144` 这些数字当时就在屏幕上，只是被当成了症状而不是证据。

## 九、进度与缓存：用户真正在乎的东西

功能做得再多，用户最在乎的其实是两件小事：**打开就能接着上次看**，以及**别让我重扫**。

**进度**存成一行文本：`完整路径 <TAB> 章号 <TAB> 章内行号`，每本一行，第一行是最近在读。

**缓存**存成二进制：magic + 版本 + 文件大小 + 编码标志 + 章节数 + `[长度, 章名, 偏移]` 数组。文件名是**路径的 FNV-1a 哈希**，放在卡根目录，八位十六进制加 `.CIX`——因为 FAT 写入层只支持 8.3 名。

这套设计带来一个副作用：**书一搬家，缓存和进度就全失效**（哈希变了、路径变了）。所以后来补了两条兜底：

1. 进度匹配时，完整路径对不上就**按文件名再匹配一次**；
2. 进度章号超出当前索引（只扫了前 30 章）时，**先续扫到那一章再打开**，而不是直接夹到最后一章——否则一退出就把"第 200 章"写成"第 29 章"。

第二条尤其重要：它不是"少一个功能"，而是**把用户的进度悄悄写坏**。这类 bug 比崩溃更可恶。

## 十、蓝牙翻页器

最后一个功能是蓝牙翻页：躺床上不想伸手。

实现上有两个决定：

**一是当 BLE 客户端（Central），不是外设。** 遥控器是 HID 外设，我们连它、订阅 HID 服务的 Report 特征（`0x2A4D`）。

**二是存原始报文，不解析报告描述符。** HID Report Map 的解析是出了名的麻烦，而翻页器只发几个字节。所以做成"学习"：屏幕上依次提示"请按上一页/下一页/上一章/下一章"，每按一次就把那串字节记下来，存进卡里的 `BTMAP.TXT`。之后按字节比对匹配。

这样做的好处是**不挑遥控器型号**——不管是发翻页键、音量键还是方向键，按下什么就记什么。

还有一个必须遵守的约束：**BLE 回调里绝对不能画屏**。回调跑在另一个任务里，而屏和卡共用 SPI，在回调里刷屏会直接把卡带掉线。所以回调只往队列里塞数据，所有动作都在主循环里执行。

## 十一、这块板的硬限制

做完之后回头看，很多痛苦不是代码问题，是板子的设计决定的：

| 限制 | 后果 |
|---|---|
| 屏和卡共用 IO1/IO4/IO6，且 IO4 方向相反 | 两者**不能同时通信**，切换必须重配 GPIO |
| 卡没有独立电源开关 | 卡锁死只能整机断电，软件救不回来 |
| CARD_DETECT 未接 GPIO | 无法检测插拔，只能发命令试探 |
| 卡 CS 串 22Ω、滤波仅 10µF | 速度上不去；屏刷新时 3.3V 一抖就掉卡 |
| CS 只有 IO21，且不能挂硬件 SS | 只能手工控制片选 |
| 没有总线隔离器件 | 全靠软件时序硬切，切错就互相干扰 |
| 屏 LDO 受 SW1 拨档限制 | 拨错档位，IO0 根本关不掉屏电 |
| IO8/IO10 与拨轮键复用 | 屏忙时不能读按键 |
| 4MB Flash 无 OTA 余量 | 加大功能（如 BLE）就得放弃 OTA |

## 十二、复盘：十条教训

1. **一版只改一件事。** 同时改三个地方，出问题就不知道是哪个。
2. **先要日志，再改代码。** 这一次排查里，绝大多数时间浪费在"我觉得是 X"上。
3. **没有日志就写诊断固件。** 一段 100 行、不依赖任何库的程序，胜过十次盲改。
4. **不要把自己的猜测说成结论。** "卡坏了"这个结论我下过两次，两次都错。
5. **别动已经能用的东西。** 有一版为了"优化"把能读的卡改到不能读。
6. **错误处理的顺序也是逻辑。** 写失败就复位，复位又失败，最后把设备写死——这种"越修越坏"的重试要有上限。
7. **状态机的每条返回路径都要能走回去。** 否则用户会卡在某个页面。
8. **API 的返回值要读全。** `CMD0` 的 `0x00` 和 `0x01` 都是合法应答，只认一个就会把活设备判死。
9. **用户感知的"坏了"，往往是某条静默的降级路径。** 进度被写坏比程序崩溃更讨厌。
10. **硬件限制不是 bug，是前提。** 与其抱怨，不如把它们列成表，设计时直接绕开。

---

## 结尾

这台机器最后能用，但过程远谈不上优雅：六七个版本的掉卡排查、两次错误的硬件结论、一次把能用的代码改坏。

不过它也确实做到了最初想要的：一页 19 行、按一下翻页、断电不丢进度、看完一章不用等。

如果要从这段经历里留一句话，大概是这句：

> 嵌入式项目里，最难的部分从来不是"写功能"，而是"搞清楚你到底在和什么打交道"——屏幕的刷新物理、卡的编程时序、总线的电平争用，这些东西不会因为代码写得好就消失。

它们只能被理解，然后被绕过。
